# 103: Name a Variable After What It Holds

Name a variable after what it holds, not after an incidental role. Whether the name also carries the type depends on the kind of type; when in doubt, follow the most common pattern in portal for that type.

- **Custom types** (any class other than `String`, a primitive, a boxed primitive, or a collection) carry the type name. A lone value of the type takes the type name itself (`user`, `layout`, `jsonObject`, `ddmStructure`), and a qualified value puts the qualifier before the type name (`scopeGroup`, `parentLayout`, `responseJSONObject`, `agentDefinitionsPage`). A qualifier alone, such as a `JSONObject` named `response`, drops the type the reader expects to see.
- **`String`, primitives, and boxed primitives** are named for their content and take no type suffix: `String name`, `long groupId`, `int port`, `Long count`, `Boolean active`. Add a type or form word only to tell values apart or to say the value is held in a different form than its plain name suggests: a `String` that holds JSON ends in `JSON`, as in `objectDefinitionJSON`, and a `String` form of a value that also exists as an object can end in `String`.
- **Collections and arrays** take the plural and need no type suffix: `String[] ids` and `List<String> ids` are both correct. A suffix such as `idsArray` or `idsList` is optional, and only earns its place when two collections of the same content share a scope; even then, one of them can stay the plain plural. A `Map` may be named for its content (`attributes`) or with a `Map` suffix (`nameMap`); both are common. A qualifier alone is not enough: when two descriptor maps are in scope, they are `ableDescriptorMap` and `bakerDescriptorMap`, not `able` and `baker`.

This applies in Groovy and Gradle scripts as much as in Java.

**Rationale:** A name that says what the value holds tells the reader what they are handling without tracing back to the declaration. A name taken from an incidental role (`metadata`, `userValue`, `result`) hides that, and invites a mismatch between the name and the value. On a custom type, the type name is what portal readers expect to find, so a qualifier alone reads as a different kind of value. On a `String`, a primitive, or a plural collection, a type suffix earns its place only when it resolves a real ambiguity; otherwise it is noise, and portal code almost never uses one.

A violation is a variable named for an incidental role rather than what it holds; a name whose stated type or form does not match the value, such as a `String` of JSON named `objectDefinitionString` rather than `objectDefinitionJSON`, or a collection named as if it held a single element; or a value named by a qualifier alone, such as a `Map` named `able` next to another descriptor map, or a `JSONObject` named `response` rather than `responseJSONObject`. A `String`, primitive, boxed primitive, collection, or array without a type suffix is not a violation, as in `String name`, `long groupId`, `Long count`, `String[] ids`, or `List<String> ids`, unless a similarly named variable in the same scope makes it ambiguous. Do not suggest adding a type suffix to such a name.

**Example:** commit `a8af2ca` renamed `metadataJSONObject` to `jsonObject`; `ec36099` renamed `objectDefinitionString` to `objectDefinitionJSON` because it holds JSON; `84d9629` renamed `getAgentDefinitions` to `getAgentDefinitionsPage` because it returns a `Page`; `320d3dc` renamed the vague `result` to `json`, the JSON that `getJSON` returns. In a Gradle test script that read two descriptor maps, the `Map` locals `able` and `baker` became `ableDescriptorMap` and `bakerDescriptorMap`.
